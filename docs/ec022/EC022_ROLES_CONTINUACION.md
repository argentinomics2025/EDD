# EC-022 — Continuación después del fallo SET ROLE

El usuario informó que las ACL anon/authenticated quedaron `f,f,t,t` y que la prueba falló al intentar `SET ROLE ec022_ingestor` después de insertar la serie sintética `test`. El script `ec022_roles_continuar.ps1` inspecciona esa fixture y conserva todos sus registros. Usa un identificador sintético diferente por ejecución; no borra datos y permite repetir la batería sin confundir ejecuciones anteriores.

El script verifica las dos migraciones aplicadas y no las repite. Comprueba el privilegio efectivo de `service_role` sobre la función de escritura exclusiva. Si existe, prepara una migración incremental local para revocar únicamente ese EXECUTE directo; si el permiso continúa por herencia, la migración falla con rollback y no modifica membresías ajenas. El diagnóstico muestra ACL, default ACL y cadena de roles. La restricción se debe revisar también en producción antes de cualquier despliegue; la existencia de BYPASSRLS no concede por sí misma EXECUTE sobre una función.

Antes de las pruebas se verifica que REST responda y que los tres roles utilizados (`anon`, `ec022_ingestor`, `ec022_validador`) puedan asumirse o que el ejecutor tenga ADMIN OPTION para un otorgamiento temporal. Cuando es necesario, se otorga únicamente `SET` al ejecutor para la ventana de pruebas, sin herencia para grants nuevos. Un bloque `finally` revoca el grant propio o restaura su opción SET anterior aun si una prueba falla, y comprueba el estado resultante antes de publicar. Una terminación forzosa del proceso o una caída simultánea de la base puede impedir cualquier limpieza; si el script informa error de limpieza deben inspeccionarse las membresías antes de continuar.

La prueba SQL conserva sus aserciones de seguridad, añade una aserción para `service_role`, ejecuta el lote en una transacción y conserva el caso de rollback mediante un savepoint. Sus aserciones de filas se limitan a la fixture de ejecución y se añade un control global contra exposición de observaciones no aprobadas. Los ensayos del escritor y la concurrencia usan el mismo identificador único.

Se verificó en PostgreSQL 17 aislado, con ejecutor CREATEROLE no superusuario: la corrección de un EXECUTE directo de `service_role`; fallo y rollback frente a EXECUTE heredado; los tests SQL, escritor y concurrencia con SET temporal; y restauración de un grant existente con SET inicialmente falso. Las 28 pruebas unitarias pasan. El script PowerShell pasó análisis sintáctico pero **no se ejecutó de extremo a extremo en el stack Supabase del usuario** desde Codex, que sigue sin acceso a Docker.

Con `-Publicar`, se envía la rama solo después de pasar las pruebas y restaurar los grants temporales. El script conserva datos, migraciones anteriores y otros stacks; no enlaza ni modifica producción o EC-021.
